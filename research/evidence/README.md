# 规范能力证据账本（Experimental）

> 本目录是一个试点层：把人物评价的编码单位从 `D1-D8` 维度下沉到 `capability_pool.md` 中的规范能力 ID。
> `D1-D8` 只作为后续汇总和展示层，不作为事实卡的直接标注对象。

## 目标

现有链路已经做到：

```text
profiles 原始资料
→ facts/F##.md 原子事实与原子能力
→ capability_pool.md 规范能力库
→ capability_matrix.md 人×能力明账
→ scores.md 八维评分
```

本目录增加一层更细的证据账本：

```text
facts/F##.md
→ evidence/F##_Name.md 逐人逐规范能力证据卡
→ capability_matrix.md
→ scores.md
```

这样每个 `D1-D8` 分数都不直接来自“此人这一维强不强”，而是来自规范能力 ID 的命中、角色强度、影响范围和置信度。

## 编码单位

每条记录必须指向 `capability_pool.md` 中的规范能力 ID，例如 `D1.1`、`D2.3`、`D7.4`。不得直接写“D1 强”或“D8 弱”。

当前 `capability_pool.md` 文本多处写“42 条规范能力”，但按可见 ID 计数为 41 条：

- `T1-T2`：2 条
- `B1-B2`：2 条
- `D1.1-D8.4`：37 条

本试点先按现有 41 个 ID 编码，不新增能力。若后续发现确有缺口，再新增规范能力或修正文档计数。

## 判定状态

| 状态 | 含义 |
|---|---|
| `confirmed` | 当前 facts 中有明确事实支持，且角色强度、影响范围与该能力定义吻合 |
| `partial` | 有事实支持，但角色、影响范围、时间点或定义边界不够充分 |
| `insufficient` | 资料可能有关，但当前 facts 不足以判定 |
| `not_found` | 当前 facts 未见支持 |
| `contested` | 支持与反证并存，需要单独仲裁 |

## 字段说明

| 字段 | 说明 |
|---|---|
| 能力ID | 必须来自 `capability_pool.md` |
| 判定 | `confirmed/partial/insufficient/not_found/contested` |
| 支持事实 | 引用 `F#` 和必要的 `C#`，不要只写总结印象 |
| 角色强度 | 主导、共同主导、创建者、统帅、参与、公共发声、未知等 |
| 影响范围 | 行业级、产品级、机构级、生态级、公共议程级等 |
| 限制/反证 | 为什么不是更高确定性，或为什么不应过度解释 |
| 置信度 | `high/medium/low` |

## 试点读法

试点文件采用稀疏账本：完整扫描规范能力库，但正文只展开 `confirmed/partial/insufficient/contested` 项；其余 ID 汇总为 `not_found`。这样避免 60 人全量时产生大量空行，同时仍然保持“以规范能力 ID 为单位”的编码原则。

试点文件末尾的“对现有明账的校正提示”只表示该证据账本暴露出的疑点，不自动修改 `capability_matrix.md` 和 `scores.md`。

## 覆盖缺口审计

证据账本最怕的不是编码争议，而是底层 facts 漏掉关键成果。每个人进入 evidence 前，应先做一次覆盖缺口审计：

1. 用此人的姓名中英文、主要机构和代表方向检索 `profiles/` 与 `facts/`，确认是否只覆盖了叙事主线。
2. 对照外部权威简介、论文作者页、项目仓库、奖项/报告页，列出候选硬成果。
3. 每个候选成果先判定“是否足以进入 FACT”，再进入规范能力编码；不直接把搜索结果写成分数。
4. 对没有补足证据的候选项，在 evidence 的校正提示里写成“待审计候选”，避免它被误判为 `not_found`。

刘铁岩试点暴露了这个问题：初版 facts 漏掉 LightGBM，导致 `D1.1` 和 `D2.2` 被低估。补入后，这类贡献应作为“被广泛使用的高效机器学习基础工具/开源框架”编码，而不是只用 learning to rank 和教育转型概括。
